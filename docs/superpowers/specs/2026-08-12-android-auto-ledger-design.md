# 安卓自动记账 App — 设计规格

**日期：** 2026-08-12  
**项目目录：** `记账/`  
**状态：** 已通过头脑风暴确认（含借鉴喵喵记账的修订）  

## 1. 目标与成功标准

做一个可下载安装的安卓记账产品：用户付款时自动感知，弹出居中确认卡片，选择消费类型后入账；支持多用户注册登录与云同步。

产品思路可参考市面「喵喵记账」等自动记账 App 的成熟做法（双通道捕获、识别场景、运行状态通知、分步权限引导），交互与品牌保持自有方案。

**第一版验收标准：**

- 微信 / 支付宝付款后能弹出确认卡并完成入账（银行 / 云闪付等按「识别场景」开启的应用尽量覆盖）
- 通知监听与无障碍读付款页两条通道至少一条能触发；通知栏能显示自动记账运行状态
- 用户可在「识别场景」中开关要监控的应用
- 预置分类可增删改；账本可查、可简单统计、可导出 Excel/CSV
- 注册登录后换机可拉回流水
- 他人可通过下载链接安装 APK 并完成上述流程

## 2. 范围

### 2.1 包含（第一版）

- Android 原生客户端（Kotlin）
- FastAPI 后端：注册/登录、分类与流水云同步、导出所需数据接口
- **双通道**自动捕获付款（通知监听 + 无障碍读付款成功页）→ 居中卡片强制确认入账
- 「识别场景」：用户自选监控哪些支付相关应用
- 通知栏常驻 / 可查看「自动记账运行中」状态
- 分步权限引导（无障碍、通知使用权、悬浮窗、电池白名单等）
- 本地 Room 优先，联网后同步
- 签名 APK + 简单下载页或 GitHub Releases

### 2.2 不包含（第一版）

- iOS
- 应用商店上架
- 家庭共享同一账本 / 实时协作
- 复杂预算、多币种、投资账户
- 读取支付 App 私有加密数据库或非用户可见的内部接口
- 抄袭喵喵记账或其他竞品的 UI / 文案 / 品牌资源

## 3. 用户与核心场景

- **角色：** 多用户，各自独立账号与账本
- **主场景：** 付款成功 →（通知或付款成功页被识别）→ 居中确认卡 → 下拉选择消费类型（必选）→ 可选备注 → 确认入账 → 本地保存并异步同步
- **约束：** 检测到付款后**必须入账**，不提供「忽略」；若当时无法操作，进入本机「待确认」队列，直到确认完成
- **配置场景：** 打开「自动记账」→ 完成权限引导 → 在「识别场景」勾选微信 / 支付宝 / 银行等 → 通知栏显示运行中

## 4. 架构

```
Android App (Kotlin)
  ┌ 通知监听服务 (NotificationListener)
  │         ╲
  │          ╲→ 付款解析器（统一去重）→ 居中确认弹窗
  │          ╱
  └ 无障碍服务 (Accessibility，读付款成功页)
  通知栏：自动记账运行状态
  「识别场景」配置 → 过滤监控包名
                              ↓
                         本地 Room DB ←→ 账本 / 统计 / 分类 / 导出 UI
                              ↓ HTTPS
FastAPI 后端
  注册登录(JWT) · 流水同步 · 分类同步 · 导出数据
  存储：第一版 SQLite，可迁移 PostgreSQL
                              ↓
APK 分发：下载页 / GitHub Releases
```

**技术选型依据：** 自动记账依赖 Android 通知与无障碍能力，故客户端原生 Kotlin；后端用 FastAPI 以匹配既有 Python 经验，并支撑多用户产品化。

## 5. 客户端功能设计

### 5.1 付款捕获（借鉴喵喵：双通道）

**通道 A — 通知监听**

- `NotificationListenerService` 读取已开启「识别场景」的应用付款通知
- 适合微信等通知文案较完整的场景

**通道 B — 无障碍读页**

- `AccessibilityService` 在付款成功 / 账单结果页解析金额、商户等节点文本
- 适合通知不全、但成功页信息完整的场景（与喵喵等产品同类做法）

**共用规则**

- 解析字段：金额、商户（或摘要）、来源、时间、捕获通道
- 去重键：来源 + 金额 + 时间窗（及通知 / 页面特征），两通道命中同一笔只入一次
- 「识别场景」：预置微信、支付宝、常见银行 / 云闪付等包名列表，默认常用项开启，用户可开关并保存
- 可选（默认关闭）：读取银行短信作为补充；不阻塞主路径

### 5.2 确认弹窗（外观与交互已定稿）

- **形态：** 居中卡片，压暗背后界面（需悬浮窗 / 全屏 Intent 等权限）
- **展示：** 来源标识、金额（大号）、商户、消费类型下拉、备注（可选）
- **唯一主操作：** 「确认入账」（无「忽略」）
- **视觉方向：** 纸感浅底、青绿主按钮、清晰层级（头脑风暴稿 `popup-look-v3`）
- **解析失败：** 仍弹窗，金额 / 商户允许手改后再入账
- **弹窗被系统拦截：** 状态栏「待入账」通知（与「运行中」状态区分），点击进入同一确认页

### 5.3 分类

- 预置：餐饮、交通、购物、住房、娱乐、医疗、教育、其他
- 用户可在设置中增删改、排序
- 确认入账前必须选择分类

### 5.4 账本 UI（第一版）

- 流水列表（按日分组）
- 简单统计（按日 / 月支出汇总、按分类占比即可）
- 分类管理
- 手动补记（含收入，作为补充入口）
- 导出 Excel/CSV
- **自动记账设置页：** 总开关、识别场景、权限状态检查
- **引导页（分步）：** 无障碍 → 通知使用权 → 悬浮窗 → 通知栏（运行状态）→ 电池白名单 / 后台运行

### 5.5 运行状态（借鉴喵喵：通知栏反馈）

- 自动记账开启且核心服务可用时，通知栏展示「自动记账运行中」（可做成低打扰常驻）
- 无障碍或通知监听被系统杀掉 / 关闭时，状态变为「已停止」，引导用户重新开启
- 便于用户判断「这次没弹窗是不是服务挂了」，而不是误以为没付款

### 5.6 本地数据与待确认

- Room 表：用户会话缓存、分类、流水、待确认付款、识别场景配置、同步元数据
- `PendingPayment` 仅存本机；确认后写入 `Transaction` 并标记待同步

## 6. 后端与同步

### 6.1 实体

| 实体 | 说明 |
|------|------|
| User | 邮箱 + 密码（第一版）；JWT；手机号登录留后续 |
| Category | 预置种子 + 用户自定义 |
| Transaction | 金额、商户、来源、分类、备注、发生时间、客户端幂等 ID |
| SyncCursor | 每用户增量同步游标 |

说明：「识别场景」、待确认队列仅存客户端本地，不同步到服务端。

### 6.2 同步规则

- **本地优先：** 确认入账先写 Room，再 `pending_sync` 上传
- **增量：** 上传未同步变更；拉取服务端自游标以来的增量
- **冲突：** 个人账本冲突极少，以最后修改时间为准
- **幂等：** 客户端生成稳定 ID，服务端去重
- **未登录：** 允许本地强制入账；登录后批量上传

### 6.3 API 能力（逻辑分组）

- 认证：注册、登录、刷新令牌
- 分类：列表、创建、更新、删除、同步
- 流水：同步推送 / 拉取、按条件查询（供统计与导出）

## 7. 权限与异常

**必开（自动记账）：**

- 无障碍服务（读付款成功页）
- 通知使用权（读付款通知）
- 悬浮窗（或等价展示能力，弹出居中确认卡）
- 通知栏权限（展示运行状态 / 待入账）
- 后台运行 / 电池白名单（降低被杀概率）
- 网络（登录与云同步）

**可选：** 短信。

**异常处理：**

- 仅开一条捕获通道时，另一条失败不阻断；两条都不可用则引导修复权限
- 解析失败 → 弹窗手改后入账
- 弹窗被拦 → 「待入账」通知接力
- 断网 → 本地入账，恢复后同步
- 重复事件（双通道）→ 幂等去重

**已知限制：**

- 依赖支付 App 通知文案与成功页结构，对方改版需更新解析 / 无障碍节点规则
- 部分国产机需用户手动锁后台、自启动；无障碍可能被系统回收
- 应用双开可能导致监听不稳定（第一版文档中说明即可）
- 无法读取支付 App 私有加密流水

## 8. 分发与隐私

- 签名 APK；下载页或 GitHub Releases 提供安装包与版本说明
- 下载页写明：允许未知来源、完整权限清单、隐私说明
- 隐私要点：无障碍与通知仅用于识别收付款信息以完成记账；确认入账后的流水按用户账号同步；不出售数据；不采集与记账无关的屏幕内容
- 第一版不上应用商店；可后续加应用内检查更新

## 10. 测试要点（第一版）

- 真机：微信 / 支付宝实付，分别验证「仅通知」「仅无障碍」「双开」命中与去重
- 识别场景关闭某应用后，该应用付款不再触发
- 通知栏运行状态：开启 / 杀掉服务后文案正确
- 去重：短时间重复通知或双通道同时触发不产生两笔
- 离线入账后恢复网络能同步
- 登录换机（或清数据重装）后流水可拉回
- 缺任一核心权限时，引导页能阻断并指引开启
